# OSAC-1415 upgrade execution alternatives

**Decision for Phase 1:** Use the AAP upgrade-only path in [design-phase1.md](design-phase1.md). Direct operator patching is deferred. This note records the reasons, risks, and work needed to reconsider that choice; it is not a second implementation contract.

**Evidence snapshot:** Local `osac` checkout at `515ce87588967055537a8fd8e7edb0e2d728eb85` and `enhancement-proposals` at `feb0108ae7c1618ded401c452e81e5f6664f57e7`. The direct-patch design before the AAP switch is available with `git show 875f71cb^:enhancements/OSAC-1415-cluster-upgrade-caas/design-phase1.md`. Recheck the code before implementing either path. The upgrade-specific code described below is proposed, not implemented in that snapshot.

## What the current code does

- Fulfillment builds `ClusterOrder.spec.nodeRequests` from `Cluster.spec.node_sets`. A size change changes `numberOfNodes`; the scale CLI sends an update with mask `spec.node_sets` (`fulfillment-service/internal/controllers/cluster/cluster_reconciler_function.go:510`, `fulfillment-service/internal/cmd/cli/scale/scale_cmd.go:157`). Phase 1 proposes adding each node set's resolved release image to its `NodeRequest`.
- The `ClusterOrder` controller currently hashes the whole spec to decide whether to run the provisioning lifecycle. A changed node count therefore triggers the AAP create/scale path (`osac-operator/internal/controller/clusterorder_controller.go:1227`, `osac-operator/pkg/provisioning/provision_lifecycle.go:59`).
- The AAP provider serializes the `ClusterOrder` into job variables at launch. The playbook reads that snapshot and acquires its per-cluster lease later (`osac-operator/pkg/provisioning/aap_provider.go:261`, `osac-aap/playbook_osac_create_hosted_cluster.yml:6,43`). Acquiring the lease does not refresh the snapshot or order jobs by when their API requests were accepted. The lease role defaults to zero retries unless its caller supplies a value (`osac-aap/collections/ansible_collections/osac/service/roles/lease/tasks/main.yaml:28`); verify its waiting behavior when implementing upgrade jobs.
- The current AAP create/scale role submits HostedCluster and NodePool definitions with `state: present`. Its NodePool definition contains `replicas`, `management`, `platform`, and `release.image` (`osac-aap/collections/ansible_collections/osac/service/roles/hosted_cluster/tasks/create_hosted_cluster.yaml:146`, `build_nodepools.yaml:14`). For an existing resource, the vendored `kubernetes.core.k8s` module merge-patches supplied fields; omitted fields are not a full-spec replacement (`osac-aap/vendor/ansible_collections/kubernetes/core/plugins/module_utils/k8s/service.py:421`). A stale supplied value can still overwrite the live value.
- Separately, `osac-operator/internal/controller/baremetalworker/nodepool.go:69` patches only `spec.replicas`. Thus “scaling only patches replicas” describes this controller action, not the entire scale flow. The operator already has NodePool `patch` and `update` RBAC; HostedCluster access is read-only (`osac-operator/config/rbac/role.yaml:84`).

## The two paths

| Consideration | AAP upgrade-only branch (selected) | Direct operator patch (deferred) |
|---|---|---|
| Image write | An upgrade-mode run of the configured AAP cluster job patches only the selected existing HostedCluster or NodePool `spec.release.image`. | The operator compares the desired and live image and patches only that field on the selected existing resource. |
| Coordination with create/scale | The operator must prevent an upgrade-mode job and a create/scale job for the same cluster from overlapping, then re-read the latest `ClusterOrder` before launching the next job. The AAP lease is an additional guard, not a replacement for this rule. | AAP may still run create/scale jobs. To permit concurrent scaling safely, AAP must set images on creation but omit `spec.release.image` when updating existing HostedClusters and NodePools. |
| Benefits | Keeps HostedCluster image writes in the existing AAP execution identity; no new HostedCluster write permission for the operator. Jobs use the existing AAP operational path. | Starts the image change without AAP scheduling or availability; avoids upgrade-specific AAP job tracking. Narrow image and replica patches can coexist at the Kubernetes field level. |
| Costs | Adds an upgrade branch to the configured job or workflow, separate job state and retries, duplicate-launch protection, and guards so install, infrastructure, readiness, and post-install tasks do not run. AAP delay or failure delays the image patch. | Adds HostedCluster patch RBAC and another image mutation path. AAP create/update behavior needs a reliable field-ownership split, including template hooks and older `ClusterOrder` compatibility. |
| Scaling during an upgrade | The selected design says create/scale work waits for an active upgrade. Specify whether “active” ends after the AAP image patch or only after HyperShift reaches a terminal result. Waiting for a terminal result may delay scaling indefinitely when an upgrade is `TimedOut` but still nonterminal. | Scaling can proceed while HyperShift upgrades if AAP's existing-resource update excludes images. Kubernetes field writes then do not overwrite one another; HyperShift behavior for new bare-metal nodes during the overlap still needs deployed verification. |
| Future mutable NodePool fields | AAP jobs that apply a field from an old snapshot can conflict with another writer of that field. Job coordination and fresh inputs remain necessary. | Each new post-creation field needs an explicit owner. If AAP reapplies it on scale while the operator also patches it, the image race recurs for that field. |

Both paths require the same catalog validation, upgrade admission via `CanUpgrade`, HyperShift progress observation, and terminal feedback. An applied image patch or successful AAP job does not mean HyperShift finished upgrading. `CanUpgrade` serializes accepted **upgrades** through the Fulfillment database; it does not by itself serialize scale requests or Kubernetes writes.

## Races and boundaries to preserve

1. **Stale AAP scale snapshot versus image patch.** Suppose a scale job carries image A, an upgrade requests B, and the upgrade patch writes B first. If the scale job subsequently submits its current full NodePool definition containing A, the live image can return to A. If the scale write finishes first and the image-only upgrade patch finishes last, the final image is B and the replica change remains. Routing the image patch through AAP alone does not determine this ordering. The selected design must enforce cross-job waiting and re-evaluate the latest order; the direct path must make AAP omit images on existing-resource updates.
2. **Two narrow patches.** A patch containing only `spec.replicas` and one containing only `spec.release.image` do not overwrite each other's fields. This does not prove that HyperShift handles worker creation during an in-progress upgrade as desired. Test both operation orders on a deployed cluster before promising concurrent scaling.
3. **Separate AAP job types.** Today's provisioning lifecycle waits for its own nonterminal provision job. A proposed upgrade job tracked separately needs an explicit cross-type guard. Persist job identity across reconciles and restarts, wait for the other job type, and fetch current desired state before dispatch. The lease alone protects only participants that acquire it and cannot repair an old job payload.
4. **API-level node-set update.** The current scale CLI clones the Cluster and updates the entire `spec.node_sets` map. Once node sets also carry a version, a concurrent scale request can carry a stale version value. Depending on future admission checks, that may overwrite the newer version or cause the scale request to be rejected. This risk exists with either execution path; use a size-only update mask or an equivalent concurrency check when adding node-set versions. Do not infer that job serialization protects the earlier API update.
5. **Field ownership beyond images.** AAP's `state: present` update is a merge patch, so omitted fields are preserved, while fields included in its definition can be reset from a stale job. Future features should record who writes each mutable HostedCluster or NodePool field after creation. Disjoint writers need no global lock; overlapping writers need a single owner or serialization with a fresh desired-state read.

## Requirements before implementing direct patching later

1. Recheck the current scale and AAP paths against the code at implementation time, including template hooks and the actual deployed RBAC. Treat the earlier direct design at `875f71cb^` as background, not as code that already exists.
2. Keep image fields out of the create/scale `DesiredConfigVersion` hash. AAP must set the selected control-plane and per-node-pool images when creating resources, and preserve live images on updates to existing resources. Prove with a real Kubernetes API test that an AAP job carrying an older `ClusterOrder` snapshot cannot revert either a HostedCluster or NodePool image.
3. Give the operator only the additional HostedCluster permission it needs. Validate namespace, named target, tenant/`ClusterOrder` association, and resource existence; never create a missing target as a side effect of upgrade reconciliation. Patch only `spec.release.image`, and make retries and restarts idempotent.
4. Keep upgrade status tied to HyperShift observation and the accepted component/target, not to patch success. Preserve terminal history and `CanUpgrade` rules independently of scale/provisioning status.
5. Test scale-before-upgrade and upgrade-before-scale, including a stale AAP snapshot, an operator restart, and new nodes while a NodePool upgrade is in progress. Use a deployed HyperShift environment for the last case; isolated API tests cannot establish worker-version behavior.
6. Resolve the API-level `spec.node_sets` update race and decide explicitly whether scale execution may overlap a HyperShift upgrade. Do not add a scale lock solely to protect disjoint Kubernetes fields; introduce one only if deployed behavior or shared-field ownership requires it.

The selected AAP path should also get explicit tests for both scale/upgrade orderings, job launch and status persistence across restart, lease contention, stale snapshots, and the upgrade branch skipping all install and post-install work. The current Phase 1 test plan covers upgrade routing and later scaling but does not yet establish those concurrency boundaries end to end.
